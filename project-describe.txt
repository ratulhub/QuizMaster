# 1. COMPLETE PROJECT INTRODUCTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHAT THE PROJECT IS:
QuizMaster is a dynamic, multi-modal, gamified web application. It is a monolithic 
Java-based platform that allows users to take quizzes in various competitive modes, 
earn XP, rank up, and compete on leaderboards.

WHY IT WAS BUILT & PROBLEM IT SOLVES:
Traditional quiz applications (like Canvas, Moodle, or basic Google Forms) are 
static, boring, and feel like homework. They lack engagement. QuizMaster solves 
this by introducing "gamification"—turning learning into a game. 

TARGET USERS & REAL-WORLD USE CASE:
- Students preparing for exams who want a fun way to test their knowledge.
- Teachers wanting to host interactive, competitive classroom quizzes.
- Friends looking for a multiplayer trivia experience.

WHY THIS SYSTEM IS BETTER:
Instead of just showing questions and answers, QuizMaster uses specialized game 
modes like "Sudden Death" (one mistake = game over) and "Roast Mode" (AI insults 
the user for wrong answers). It features a cinematic, premium UI that feels like 
a modern startup product rather than a dusty academic tool.

# 2. COMPLETE TECHNOLOGY STACK
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

We chose a robust, foundational technology stack to demonstrate a deep understanding 
of how the web works underneath the hood, avoiding "magic" frameworks.

JAVA
- Purpose: The core backend programming language.
- Why Used: It is strongly typed, highly scalable, and the industry standard for 
  enterprise applications. It forces good object-oriented design.

JSP (JavaServer Pages)
- Purpose: To create dynamic web pages.
- Why Used: It allows us to write HTML and inject Java variables directly into 
  the page before it is sent to the browser.
- Advantage: Fast server-side rendering without needing a complex React frontend.

SERVLETS (Jakarta EE)
- Purpose: To handle HTTP requests (GET, POST).
- Why Used: Servlets are the absolute foundation of Java web development. By using 
  raw Servlets instead of Spring Boot, we demonstrate that we understand HTTP lifecycles.

JDBC (Java Database Connectivity)
- Purpose: To talk to the database.
- Why Used: It is the raw, native Java API for executing SQL queries. It teaches 
  us exactly how database connections and transactions work manually.

POSTGRESQL & SUPABASE
- Purpose: Relational database to store users, quizzes, and scores.
- Why Used: PostgreSQL is the most advanced open-source database. Supabase provides 
  it hosted in the cloud, so our app works anywhere in the world.

HTML / CSS / JAVASCRIPT
- Purpose: The frontend interface.
- How it works: We used custom CSS variables to build a "Cinematic Glassmorphism" UI, 
  and Vanilla JavaScript to handle toast notifications, timers, and particles without 
  bloating the app with heavy libraries.

MAVEN
- Purpose: Build automation and dependency management.
- Why Used: Instead of manually downloading JAR files, Maven automatically downloads 
  libraries (like the PostgreSQL driver) and packages the project into a WAR file.

DOCKER & RENDER
- Purpose: Containerization and Cloud Hosting.
- Why Used: Docker puts our entire app (Java + Tomcat Server) into a portable container. 
  Render hosts this container live on the internet.
- Advantage: "It works on my machine" becomes "It works everywhere."

# 3. COMPLETE PROJECT ARCHITECTURE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

QuizMaster uses the classic Monolithic MVC (Model-View-Controller) Architecture.

1. FRONTEND LAYER (View): The JSP, CSS, and JS files running in the user's browser.
2. BACKEND LAYER (Controller): The Java Servlets running on the Tomcat Server.
3. DATABASE LAYER (Model): The PostgreSQL database hosted on Supabase.

COMPLETE REQUEST FLOW (Step-by-Step):
1. Browser: The user clicks the "Login" button. The browser sends an HTTP POST request 
   to the URL `/login` with the username and password hidden in the body.
2. Tomcat Server: The server receives the request and maps `/login` to the `LoginServlet`.
3. Servlet: The `LoginServlet` reads the request parameters and hashes the password.
4. JDBC: The Servlet uses JDBC to send a `SELECT` SQL query to PostgreSQL.
5. PostgreSQL: The database checks the `users` table and returns the result (ResultSet).
6. Servlet: The Servlet reads the ResultSet. If valid, it creates an `HttpSession`.
7. JSP: The Servlet uses `res.sendRedirect()` to tell the browser to go to the Dashboard.
8. Browser: The browser requests `/dashboard`, sees the dynamic JSP HTML, and renders it.

# 5. PINPOINT EXPLANATION OF EVERY JAVA FILE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

LoginServlet.java
- Exact Purpose: Handles user authentication.
- Request Flow: `doPost()` reads username/password from login.jsp. `doGet()` handles logout.
- Database Query: `SELECT id, role FROM users WHERE username=? AND password_hash=?`
- Data Movement: Uses PasswordUtil to hash input, compares it with the database hash. If it matches, it creates an `HttpSession` and sets `session.setAttribute("user", username)`.

RegisterServlet.java (Often combined with Login logic)
- Exact Purpose: Creates new user accounts.
- Database Query: `INSERT INTO users (username, password_hash) VALUES (?, ?)`
- Validations: Checks if fields are empty, hashes password before saving.
- Error Handling: Uses try-catch. If a username already exists, SQL throws a unique constraint exception, which we catch and redirect with `?error=Username+Taken`.

QuizServlet.java
- Exact Purpose: Handles the core gameplay loop. Loads questions and processes answers.
- Request Flow: `doGet()` loads the quiz page. `doPost()` receives the submitted answer.
- Session Usage: When a quiz starts, it loads a `List<Question>` and stores it in the session along with `currentIndex=0`. Each time the user answers, it increments the index.

ResultServlet.java
- Exact Purpose: Finalizes the quiz, calculates score, and updates global XP.
- Database Queries: 
  1. `INSERT INTO quiz_attempts` (saves history).
  2. `UPDATE profiles SET xp = xp + ?` (updates global ranking).
- Transaction: Disables auto-commit. Runs both queries. If both succeed, it calls `commit()`.

UploadServlet.java (Admin)
- Exact Purpose: Allows admins to add new quizzes via file upload.
- Request Flow: Uses `@MultipartConfig` to read files. Parses the file and runs multiple `INSERT INTO questions` statements.

AuthFilter.java
- Exact Purpose: Security Middleware. 
- Servlet Lifecycle: It sits between the browser and the Servlets. The `doFilter()` method checks if `session.getAttribute("user")` is null. If it is, it blocks the request and redirects to login.

DBConnection.java
- Exact Purpose: The Singleton database connector.
- How it works: Reads `DB_URL`, `DB_USER`, `DB_PASSWORD` from environment variables, automatically appends `sslmode=require` for cloud security, and returns a `Connection` object.

# 6. JDBC EXPLANATION IN DETAIL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

JDBC (Java Database Connectivity) is the API we use to send SQL from Java to PostgreSQL.

- DriverManager: The class that manages database drivers. We call `DriverManager.getConnection(url, user, pass)` to open the socket to the database.
- Connection Object: Represents the live physical connection to the Supabase server.
- PreparedStatement: We use this exclusively. Instead of pasting strings together (which causes SQL Injection), we use `?` placeholders. 
  Example: `SELECT * FROM users WHERE username = ?`. Java safely inserts the string, escaping malicious characters automatically.
- ResultSet: When we run a `SELECT` query, the database returns a ResultSet. We use `while(rs.next())` to read the data row by row.

executeQuery vs executeUpdate:
- `executeQuery()` is used for SELECT statements (returns data).
- `executeUpdate()` is used for INSERT, UPDATE, DELETE (returns the number of rows changed).

Try-With-Resources:
We write code like `try (Connection conn = DBConnection.getConnection()) { ... }`. This automatically closes the connection when the block finishes, preventing memory leaks that would crash the server.

Transaction Flow:
If we update multiple tables (e.g., in ResultServlet), we do:
1. `conn.setAutoCommit(false);` (Start transaction)
2. Run Query 1.
3. Run Query 2.
4. `conn.commit();` (Save permanently). If anything fails, `catch` block runs `conn.rollback();` to undo everything.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# 7. DATABASE EXPLANATION (TABLES & RELATIONS)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. users
- Purpose: Stores authentication data.
- Columns: `id` (UUID Primary Key), `username`, `password_hash`, `role`.

2. profiles
- Purpose: Stores gamification stats. One-to-One relationship with users.
- Columns: `user_id` (Foreign Key), `xp`, `rank_title`, `total_quizzes_taken`.

3. categories
- Purpose: Groups quizzes (e.g., Science, History). Primary Key: `id`.

4. quizzes
- Purpose: A collection of questions. 
- Foreign Keys: `category_id` (links to categories), `created_by` (links to users).

5. questions
- Purpose: Stores the actual trivia.
- Columns: `quiz_id` (FK), `question_text`, `options` (JSONB for A/B/C/D), `correct_answer`.

6. quiz_attempts (Results)
- Purpose: Historical record of every quiz taken.
- Columns: `user_id`, `score`, `xp_earned`, `completed_at`.

7. roast_messages
- Purpose: Stores the insults used in Roast Mode.
- Columns: `message`, `intensity`.

# 8. COMPLETE AUTHENTICATION FLOW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Registration: The user inputs a password. `PasswordUtil.java` hashes it using the SHA-256 algorithm. The plain text password is lost forever. Only the hash is saved to the DB.
2. Login: The user types their password. The system hashes what they typed, and compares it to the hash in the DB. If they match, authentication is successful.
3. Session Creation: `LoginServlet` calls `req.getSession()`. Tomcat creates a memory slot on the server and assigns it a unique Session ID. Tomcat sends this ID back to the browser as a secure Cookie.
4. Protected Routes: When the user requests `/dashboard`, the browser automatically sends the Session ID cookie. `AuthFilter` checks the ID, finds the server memory slot, verifies the user is logged in, and allows access.
5. Logout: `session.invalidate()` destroys the memory slot on the server.

# 9. COMPLETE QUIZ FLOW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. User selects a category and mode on `modes.jsp`.
2. They click "Start". `QuizServlet` runs a `SELECT * FROM questions WHERE quiz_id = ?` query.
3. The questions are loaded into a Java `List` and saved in the Session.
4. The user is redirected to `quiz.jsp`.
5. `quiz.jsp` displays Question 1 and starts the JavaScript timer.
6. The user submits an answer. `QuizServlet` checks if `user_answer == correct_answer`.
7. If yes, `score++`. If no (and Roast Mode is on), a random roast is pulled from the DB and shown.
8. The index increments. This repeats until all questions are answered.
9. `ResultServlet` takes the final score, calculates XP, saves to DB, and redirects to `result.jsp` where Confetti JS fires.

# 10. EXPLAIN ALL SPECIAL MODES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

- Normal Mode: 15 seconds per question. Standard scoring. 1x XP.
- Sudden Death: 10 seconds per question. 2x XP Multiplier. If the user submits even ONE wrong answer, a boolean flag is triggered, the quiz aborts immediately, and they get 0 XP.
- Roast Mode: On a wrong answer, the backend queries the `roast_messages` table, selects a random string, and stores it in the session. `quiz.jsp` detects this and flashes a massive red insult on the screen.
- Panic Mode (Concept): The timer starts at 15s. For question 2, it's 13s. For question 3, 10s. The JS timer dynamically reads the `currentIndex` from the session to speed up the countdown.
- Friend Battle: Two users enter the same room code. The backend creates a `battle_rooms` entry. Both users submit scores. The dashboard polls the database to see who won based on `battle_scores`.

# 11. COMPLETE FRONTEND EXPLANATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

We avoided heavy frameworks like React to keep the project core Java-focused. 
Instead, we built a custom "Cinematic Glassmorphism" UI.

- Glassmorphism: Achieved in `style.css` using `background: rgba(20, 20, 30, 0.4)` combined with `backdrop-filter: blur(12px)`. This creates a frosted-glass look over the background.
- Animations: We used CSS `@keyframes` to create the `animate-fade-up` utility class, which makes elements smoothly slide in when a page loads.
- JavaScript Interactions: `app.js` controls the background floating particles using a lightweight HTML5 Canvas loop. It also controls "Toast Notifications" (sleek popups that appear from the bottom right instead of ugly browser alerts).
- Quiz Timer: Handled via `setInterval` in JavaScript. If it hits 0, JS automatically submits the form via `document.getElementById('quizForm').submit()`.

# 12. COMPLETE DEPLOYMENT EXPLANATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

QuizMaster is deployed using modern DevOps practices.

Deployment Architecture:
Developer Laptop -> GitHub -> Render Cloud Platform -> Docker Container -> Supabase DB

1. Code is pushed to GitHub.
2. Render (a cloud host) detects the new commit via Webhooks.
3. Render reads the `Dockerfile` in the repository.
4. Render pulls the Maven Docker Image, runs `mvn clean package` to build the `.war` file.
5. Render pulls the Tomcat Docker Image, places the `.war` file inside it, and starts the server.
6. The Tomcat server reads the Environment Variables injected by Render to connect securely to the Supabase PostgreSQL database over the internet.

- What is Docker: A tool that packages software into standardized units called "containers". It contains everything the software needs to run (code, runtime, tools).
- Why Used: It eliminates the "it works on my laptop but not on the server" problem.
- Multi-stage Build: Our Dockerfile has two parts.
  1. `FROM maven:3.9.6 AS build`: It uses a Maven image to compile our code.
  2. `FROM tomcat:10.1`: It takes a fresh Tomcat server, copies ONLY the finished `.war` file from the first stage, and discards all the heavy source code and maven tools. This makes the final server extremely lightweight and fast.

# 14. COMPLETE MAVEN EXPLANATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

- What is Maven: A build automation tool primarily used for Java projects.
- pom.xml (Project Object Model): The heart of Maven. It contains XML tags listing our dependencies (like the PostgreSQL JDBC Driver and Jakarta Servlet API).
- How it works: When we run `mvn clean package`, Maven:
  1. Deletes the old `/target` folder (`clean`).
  2. Downloads required libraries from the internet.
  3. Compiles `.java` into `.class` bytecode.
  4. Zips everything (classes, JSPs, CSS) into a `.war` (Web Archive) file (`package`).

# 15. TEACHER QUESTION PREPARATION (VIVA Q&A)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: Why did you use raw Servlets instead of Spring Boot?
A: I wanted to demonstrate a deep, fundamental understanding of web architecture, HTTP lifecycles, and manual session management. Spring Boot abstracts too much magic away; by building this from scratch, I can confidently explain every single step of the request/response pipeline.

Q: How did you prevent SQL Injection?
A: I exclusively used `PreparedStatement` in JDBC instead of string concatenation. PreparedStatements pre-compile the SQL query structure on the database server, and treat user inputs strictly as literal string parameters, making it impossible for malicious code to be executed.

Q: What is the difference between a Session and a Cookie?
A: A Cookie is a small piece of text stored on the client's browser. A Session is a memory space stored on the Server. In this project, when a user logs in, I create a Server Session. The Server then generates a unique Session ID and sends it to the browser as a Cookie. The browser sends that Cookie back on every request so the server knows who they are.

Q: Why did you use Docker?
A: To ensure environment consistency. Tomcat requires specific Java versions and folder structures. Docker packages my application and the exact Tomcat runtime it needs into a single container, ensuring it runs identically on my laptop, on Render, or anywhere else.

Q: What happens if the database crashes while saving a quiz result?
A: Because I implemented Transaction Management by disabling auto-commit, if the system crashes after updating the attempt history but before updating the user's XP profile, the entire transaction rolls back. This guarantees database ACID properties (Atomicity), preventing corrupted or partial data.

Q: What is the purpose of the AuthFilter?
A: It enforces the DRY (Don't Repeat Yourself) principle. Instead of writing authentication logic at the top of every single Servlet, the Filter acts as middleware. It intercepts all requests to protected URLs, checks the session, and either forwards the request or redirects to the login page automatically.

Q: What is MVC and where is it here?
A: MVC is Model-View-Controller. 
- Model: Database and Java classes (like `Question`).
- View: The JSP pages, HTML, CSS.
- Controller: The Java Servlets routing the logic.
